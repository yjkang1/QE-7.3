GOAL
  hp.x currently gets Hubbard U/V by DFPT (linear response, chi0 -> chi).
  Add a second, independent estimator to the same driver: the pseudo-hybrid
  ACBN0 ratio implemented in this fork's PW/src/new_ns_v.f90.  Both then read
  ONE ground state with ONE set of ortho-atomic projectors, which makes
  U_ACBN0 and U_DFPT directly comparable.  That comparison is the paper.

  NOTE: this deliberately overrides the recommendation in
  logs/new_ns_v_review.md section 8 (which said port the occupation-matrix
  infrastructure and leave the ACBN0 kernels behind).

METHOD PAPER: S. Lee and Y-W. Son, Phys. Rev. Res. 2, 043410 (2020).

Key statements, verbatim in substance:
  - "We actively develop in the case of acbn0_type = 2 only.  If you want to
     perform DFT+U calculation, set ehub_nn_distance = 0.0 and acbn0_type = 2"
    => acbn0_type = 1 (new_ns_a0), which our whole S0-S3 chain used, is NOT
       the maintained path.  It validated perfectly against itself and against
       pw.x, but the authors' intended +U route is new_ns_e0_1 with a zero

  - remove_ehub_u(a,b) = 0 forces U of orbital b of type a to zero.  Default 1.

  - f orbitals are not available.  Confirms our Hubbard_l > 2 rejection.
  - spin-polarised is collinear-only (nspin = 2); noncollinear needs

  - ehub_pot_fix fixes occupation numbers in the Hubbard energy; the authors
    recommend a two-step workflow when eACBN0 will not converge, and note the
    difference is "usually marginal".

    r = l*a1 + m*a2 + n*a3, C and D the orbital counts.  A==B with l=m=n=0 is

ONE table.  hubbard_nns() (PW/src/hubbard_nns.f90:2) is pure geometry - it
builds ehub_nn_vect/_leng/_dim from tau, at, alat and a cutoff, touching no
bookkeeping of either flavour - and hubbard_symmetry / hubbard_get_nnc read
only that table plus stock symm_base.  So V3:

    MODULE hp_acbn0_nn   (new, inside eACBN0.f90)
        nn_csize, nn_vect, nn_leng, nn_dim, nnnc, nn_distance
        hp_acbn0_build_nn   <- hubbard_nns + the nnnc count at input.f90:2144
        hp_acbn0_symmetry   <- hubbard_symmetry
        hp_acbn0_get_nnc    <- hubbard_get_nnc   (+ BUGFIX, below)
        hp_acbn0_free_nn

    manifold + projectors  <- MODULE ldaU (Hubbard_l, Hubbard_lmax, is_hubbard,
                              offsetU, wfcU, nwfcU), exactly as S3
    neighbour set          <- built here from geometry + cutoff

WHY A CUTOFF AND NOT ldaU's neighood/at_sc.  Lee & Son define the inter-site
set by a cutoff d_IJ; the fork implements exactly that.  ldaU's neighood/at_sc
is not an alternative definition - it is how stock QE stores a pair list the
user typed into the HUBBARD card, with nb a SUPERCELL index that is painful to
write by hand.  Taking the cutoff directly is closer to the method and gives
hp.x something pw.x cannot do: sweep d_IJ without re-running pw.x.
New &INPUTHP tag: nn_distance (Angstrom).  Negative = fall back to the XML's
ehub_nn_distance, which needs a lda_plus_v run.

STATIC CHECK.  Normalised diff of the V3 kernels against V2 (all manifold and
neighbour accessors collapsed to common tokens, comments/blanks stripped):
818 code lines in ns_e0_1, and EVERY difference is one of the ten intended

 BUG 4 (upstream, latent) - hubbard_get_nnc returns nnc UNDEFINED
--------------------------------------------------------------------------------

PW/src/hubbard_nns.f90:241.  nnc is assigned only inside
    IF ( MAXVAL(ehub_nn_vect(n1+ics,n2+ics,n3+ics,:,:)) == 1 )
so a cell carrying no neighbour pair falls through with nnc untouched.
hubbard_symmetry (line 236) asks for the index of a ROTATED cell, which is not
guaranteed to be one of the occupied ones, and symmetrize_n5 then indexes
n(nnc) with whatever was on the stack.

Found by rebuilding eACBN0.f90 with -check bounds,uninit -fpe0 after V3b
segfaulted (signal 11, address 0x8c).  The optimized build gave only a useless
UCX backtrace; the checked build named it immediately:

    forrtl: severe (408): Subscript #1 of the array N has value 1059660741
                          which is greater than the upper bound of 19
    hp_acbn0_symm_n5_   3949  eACBN0.f90
    hp_acbn0_ns_e0_1_   2587  eACBN0.f90

FIX: hp_acbn0_get_nnc sets nnc = 0 on entry; hp_acbn0_symm_n5 skips the pair
when nnc == 0.  That is the correct contribution - a rotated image outside the
neighbour set contributes nothing to the symmetrised occupation matrix.

WHY IT NEVER FIRED BEFORE.  It is reachable in the fork too.  It did not fire
on the NiO_acbn0_v ground state (V0/V1/V2 all clean, and V3a is clean) but does
on the stock ../NiO one, with an identical neighbour table, identical symmetry
(12 ops) and identical manifold.  So it depends on which rotated images the
symmetrisation actually visits.  Reading uninitialised stack in an optimized
build is silent when the garbage happens to land in a mapped page - which is
exactly the failure mode this staged validation exists to catch.

Also restored: hp_acbn0_print_uv, a line-for-line copy of write_ehub_uv's
output format.  Dropping write_ehub_uv had left the V3 runs with no
pw.x-format table, which broke the diff-based checkpoints.

--------------------------------------------------------------------------------
 THE ONE CAPABILITY V3 TRADES AWAY
--------------------------------------------------------------------------------

V3's premise is that ldaU describes the manifold - and ldaU CANNOT express two
Hubbard channels on one atomic type.  Its scalar Hubbard_l(nt) names one
channel and puts any second in a SEPARATE offsetU_back block, whereas ldaV
concatenates them into a single manifold indexed by ehub_l(m,nt).

So GaAs (Ga 4s+4p, As 4s+4p), which ran under V2 and matched pw.x across 204
lines, is now refused:
    hp_acbn0_check_v (1): acbn0 = 2 needs a ground state with a Hubbard
    manifold: the pw.x run had lda_plus_u = .false. ...
An explicit refusal, not a silent projection onto the first channel.

The V2 build is preserved at HP/src/eACBN0.f90.v2bak for that case.  Making
multi-channel work under ldaU means teaching the kernels about background
channels (Hubbard_l2/Hubbard_l3, offsetU_back, ldim_back) - real work, and the
obvious next task after this one.
